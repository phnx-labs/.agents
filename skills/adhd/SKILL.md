# ADHD decision workflow

Use this as a bounded problem-solving protocol, not a diagnostic or medical tool. It creates
a decision preview only: do not modify a repository, submit work, send a message, open a PR,
deploy, access credentials, or take a production action.

## Frame and explore

1. State the decision owner, current options, constraints, success criteria, harms to avoid,
   required evidence, and the latest decision time. If the decision is missing, ask one
   concise question.
2. Read the relevant project instructions plus current source or authoritative documents.
3. Create five materially different frames by default; use fewer only when there are fewer
   real dimensions, and never exceed seven. Every frame includes its lens, evidence,
   candidate action, assumptions, and falsification test.
4. Run a critical synthesis that searches for shared assumptions, missing stakeholders,
   irreversible outcomes, and evidence that would change the leading result. Rank viable
   options against the stated criteria; record uncertainty rather than inventing consensus.

## Optional DevSub workflow

Use DevSub only when the active tool list exposes the ADHD workflow tools and the
authenticated caller has the required scope. Inspect their live schemas, then use
`adhd_ideate`, `adhd_critique`, and `adhd_promote_preview` in that order.

Never guess arguments, bypass authorization, send raw prompts to an unapproved provider, or
equate a tool call with approval. Without the tools, label the result `local draft` and state
that it lacks DevSub's server-side independence and durable audit trail.

## Close

Return the decision statement, frames, critic findings, ranked recommendation, rejected
alternatives, assumptions, confidence, and the cheapest reversible experiment. Leave the
result at the approval boundary for the normal project workflow to promote.
